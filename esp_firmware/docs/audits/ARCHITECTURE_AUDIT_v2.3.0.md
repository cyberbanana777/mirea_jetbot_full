# ESP32 Jetbot — архитектурная ревизия v2.3.0

**База:** `robot_uart_bench_v2_2_9_startup_service.zip` (проверенная пользователем аппаратная регрессия UART 7/7 PASS).  
**Режим:** аудит исходников без изменения прошивки, без автоматической компиляции и без записи в NVS.  
**Область проверки:** `esp32_firmware/*.ino`, `*.h`, `*.cpp`; результаты — статическая ревизия, не доказательство физической безопасности.
**Статус:** историческая редакция. База — v2.2.9; актуальная редакция — `ARCHITECTURE_AUDIT_v2.4.0.md` (база: ветка `fix/esp32_firmware`, 2026-11-11), там же — текущие статусы находок A-01…A-10 и новые находки A-11…A-16.

## 1. Текущая архитектура

`esp32_firmware.ino` владеет физическими объектами, общим состоянием, контекстами зависимостей и циклом планирования.

| Модуль | Назначение | Зависимости / состояние |
|---|---|---|
| `StartupService` | `setup`: Serial, Wire, периферия, NVS, начальный STOP, счётчики | ссылки на контроллер, датчики, таймеры; `config.h` |
| `SerialService` | чтение Serial/Serial1, валидация команд, диспетчеризация, сброс motion-watchdog | приёмники, `CommandContext`, watchdog, аппаратные флаги |
| `SafetyManager` | проверка тайм-аута и условий остановки, счётчик watchdog, выключение телеметрии | контроллер, таймер команды, флаги, напряжение |
| `ControlLoopService` | 100-Гц регулятор и 50-Гц одометрия | энкодеры, оценщики, контроллер, одометрия, телеметрия |
| `HardwareMonitor` | INA219, повторное обнаружение/инициализация INA/PCA/OLED | Wire, INA, контроллер, дисплей, аппаратные флаги |
| `CommandDispatcher` | STOP/движение/параметры/диагностика | `CommandContext`, `ConfigService`, `DiagnosticsService` |
| `ControlScheduler` | периоды и I²C-окно | `micros`, счётчики в `.ino` |

**Фактический порядок `loop()`:** `serialService.poll()` → `safetyManager.check()` → регулятор → одометрия → `processCommands()` → `processSecondary()` → INA → проверки I²C → OLED → LED ошибок. Этот порядок сейчас не меняем.

## 2. Точки риска и технический долг

### P1 — до новых функциональных изменений

**A-01. Проверка восстановления PCA9685 не подтверждает успех.**  
`motor_controller.cpp`, `MotorController::reinitializePWM()`: метод вызывает `_pwm.reset()`, `setPWMFreq()`, `emergencyStop()` и **безусловно возвращает `true`**. В `hardware_monitor.cpp` ветка `if (controller.reinitializePWM())` трактует `true` как успешное восстановление и сбрасывает `pwmErrors`, устанавливает `pwmOk = true`. Следовательно, на текущем программном интерфейсе не проверяется реальное появление устройства. **Рекомендация:** отдельный ограниченный change set с подтверждением I²C ACK после reinit, корректной передачей результата, fail-closed флагом `pwmOk`, и испытанием отказа на стенде; не объединять с новым рефакторингом STOP.

**A-02. Стартовые аппаратные флаги оптимистичны.**  
`esp32_firmware.ino`: `inaOk = pwmOk = oledOk = true`. В `StartupService::begin()` выполняются `soft_check_exec(probe(...))`, но результат проб напрямую не записывается в эти флаги. До первого цикла `HardwareMonitor::checkI2CDevices()` диагностика может показывать успешное состояние устройства, отсутствующего при старте. **Рекомендация:** отдельно спроектировать синхронизацию начальных флагов с проверкой инициализации; оценить последствия для fail-closed до принятия команд.

**A-03. Недостаточная аппаратная проверка STOP/watchdog.**  
`SafetyManager::check()` вызывает `emergencyStop()` только если `!controller.isStopped()`. Сама `MotorController::emergencyStop()` обнуляет четыре PWM-канала, но UART suite не измеряет выходы, не испытывает watchdog после движения и не моделирует выпадение I²C. **Рекомендация:** отдельный контролируемый моторный стенд с независимым способом остановки/обесточивания нагрузки, прежде чем утверждать физическую безопасность.

### P2 — документация и наблюдаемость

**A-04. Несогласованные комментарии о периоде I²C.**  
В `.ino` `I2C_CHECK_INTERVAL = 500` мс и рядом комментарий `0.5 секунды`; в `loop()` написано «не чаще 2 секунд». Фактическое условие — 500 мс *при наличии I²C-окна*. **Рекомендация:** исправить комментарий; не менять константу без замеров задержек.

**A-05. Нулевой порог ошибок I²C.**  
`MAX_I2C_ERRORS = 0`. В `HardwareMonitor` счётчик инкрементируется и сравнивается `>= 0`; первая ошибка сразу запускает reinit. Это текущее поведение, не обязательно ошибка; проверить, соответствует ли оно требованиям к дребезгу I²C и латентности контура. **Рекомендация:** описать порог и сценарии возврата устройства, отдельно добавить fault-injection тест.

**A-06. Разные версии приложения и протокола.**  
`VERSION = "2.4.0"` в `.ino`, в `protocol_wrapper.cpp` статический ответ `$501;2;2;#` и комментарий `major=2, minor=1`. Вероятно, речь о разных сущностях (версия прошивки и API), но комментарий у кадра внутренне противоречит полям. **Рекомендация:** явно документировать firmware version vs UART protocol version и исправить комментарий после сверки спецификации.

**A-07. Инициализация подсистемы не означает подтверждение связи.**  
`StartupService` выполняет `soft_check_exec` проб адресов и затем `check_exec` инициализации устройств; `HardwareMonitor` в ряде случаев может объявить устройство восстановленным после ACK без проверки всех функций. **Рекомендация:** различить состояния `detected`, `initialized`, `healthy` (дизайн, без автоматического изменения логики).

### P3 — поддерживаемость

**A-08. Сильно связанный application root.**  
В `.ino` находятся объекты, состояния, контексты и время цикла; это допустимо для composition root. Сохранить ownership там, вместо бесконтрольного вывода новых глобалей в `.cpp`. При росте проекта рассмотреть `AppContext` только если уменьшится число дублирующихся зависимостей.

**A-09. Сырой парсер сообщения Jetson `$6` в `.ino`.**  
`parseJetsonMessage()` использует `strtok` и копирование в буфер 128 байт, принимает 4 поля; результат — `wifi_ssid/password/ip` для OLED. Можно выделить как независимый pure parser с тестами на неполный кадр/разделители/длинные поля, но приоритет ниже safety.

**A-10. Устаревший комментарий над `i2cWindowOpen()`.**  
Докблок описывает преобразование тиков в частоту, хотя функция служит для расписания I²C. Удалить или перенести при документационной правке.

## 3. Цепочка безопасности и владение состоянием

- `SerialService` обновляет `emergency_timer` **только** после принятой валидной команды движения, прошедшей `SafetyPolicy` и проверку чисел; сбрасывает `watchdog_stop_latched`.
- `SafetyManager` до обработки команд проверяет устаревший `emergency_timer`, ошибку INA/PWM или напряжение; по тайм-ауту гасит телеметрию и один раз инкрементирует `watchdog_stop_count` до следующей валидной команды движения.
- Команда `STOP` напрямую вызывает `controller.emergencyStop()` в `CommandDispatcher`; старт и восстановление PWM используют тот же метод. Это **разные точки вызова одной реализации**, а не доказанное дублирование алгоритма.
- `HardwareMonitor` устанавливает аппаратные флаги и делает попытки восстановления. Состояние `pwmOk` особенно важно для `SafetyPolicy`; см. A-01/A-02.

## 4. Предлагаемая последовательность работ

1. **v2.3.0 audit-only:** сохранить этот отчёт; никаких изменений в firmware. Существующий UART suite 7/7 относится к базе v2.2.9.
2. **Следующий change set:** исправить только комментарии/версионирование и/или добавить unit-тесты правил watchdog без затрагивания firmware runtime.
3. **Отдельный safety fix:** изучить и исправить семантику `reinitializePWM` и начальных hardware-флагов; запросить ручную сборку и UART 7/7, а затем отдельно стендовые fault-injection испытания.
4. После подтверждения безопасности вернуться к функциональным изменениям для Jetson Nano / ROS 2.

## 5. Границы проверок

Проведено чтение исходников архива v2.2.9. **Никаких автоматических сборок ESP32 и аппаратных тестов в рамках аудита не запускалось.** Результаты UART 7/7 относятся к пользовательскому запуску v2.2.9 и не подтверждают реальные выходные уровни PWM, потерю I²C или моторный watchdog под нагрузкой.
