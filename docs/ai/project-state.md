## 1. Итоговая оценка

**Проект готов к рефакторингу локально, но не готов к интеграционному
развёртыванию.**

| Область | Оценка | Обоснование |
|---|---|---|
| Прошивка ESP32 | **готов** к дальнейшему рефакторингу | Слои выделены, политики чистые, сервисы разделены; 5 коммитов поверх `base_commit` (`b4c4e0a`) — документация, миграция v2, гигиена, границы кадра, CI; хостовые тесты регулятора проходят |
| ROS-контур (мост) | **миграция завершена** | Мост переведён на v2 (`$101` из `/cmd_vel`, `$103` по таймауту, разбор `$301`/`$202`), добавлен таймер простоя `/cmd_vel`; gtest переведён на v2-кадры |
| Интеграция ROS ↔ ESP32 | **готова на уровне кода** | Прошивка, мост, конфигуратор и стендовые инструменты используют один протокол v2; сквозной host-тест «мост ↔ прошивка» зелёный. Аппаратная проверка не выполнялась |
| Инфраструктура сборки/проверок | **готова частично** | Host-тесты протокола и границ кадра подключены к Makefile; CI (`.github/workflows/ci.yml`) запускает 4 job без ROS 2. Остаются библиотека `uPID` (R-12) и `colcon`-сборка ROS-пакетов — вне CI |
| Безопасность | **ограниченно готова** | Fail-closed политика по питанию и периферии реализована; диапазонная проверка motion-значений отсутствует (R-07 — оставлена по решению владельца, задокументирована); аппаратного отключения питания моторов нет; нулевой PWM не подтверждён измерением |
| Документация | **исправлена (Этапы 1-2, 5)** | PROTOCOL.md, README моста, README прошивки, CHANGELOG приведены в соответствие с кодом; `docs/ai/` создана и обновлена; журнал аппаратных тестов приведён в соответствие с фактическими прогонами |

**Ключевой вывод.** Проект не требует переписывания: основная работа уже проделана
в ветке. После Этапа 2 разрыв протокола закрыт, после Этапа 5 — убраны осиротевшие
артефакты, после Этапа 6 — появился CI, защищающий договорённости v2 от
повторного расхождения. Оставшиеся ограничения — отсутствие библиотеки `uPID`
и **непроверенная на железе** повестка.

## 2. Подтверждённые проблемы

### R-01 (блокирующий). Разрыв протокола между ROS-мостом и прошивкой

**Факт.** Прошивка реализует только v2 (`command_parser.cpp:decodeCommand` — ID
101…501). Рабочий `serial_bridge_cpp` реализует только v1: шлёт `$1;%.3f;%.3f;#`
(`serial_bridge_node.cpp:128`) и ждёт тип кадра 1 или 2
(`serial_bridge_node.cpp:53-54,229,233`).

**Следствие.** Команда `$1;v;w;#` на прошивке даёт `UNKNOWN` → отбраковка и
инкремент `rejected`; кадр `$301;...;#` мостом не распознаётся → WARN
«Unexpected frame (type 301, 8 fields)». Ни движение, ни одометрия в связке не
работают. **[Код]**

**Доказательство.** `esp_firmware/tests/test_bridge_v2.cpp`, собранный против
рабочего `serial_bridge_cpp/include/serial_bridge_cpp/frame_parser.hpp`, падает с
assertion на `!parse_fields("$301;nan;#", values)` (exit 134, core dumped); та же
проверка против `esp_firmware/serial_bridge_cpp_reference/...` проходит (exit 0).
**[Код]**

**Дополнительно.** Рабочий парсер не проверяет конечность: `frame_parser.hpp:136-139`
использует `strtod` и отбрасывает только `num_end != sep || errno == ERANGE` —
значения `nan`/`inf` проходят и попадают в публикуемую одометрию. **[Код]**

**Где лежит готовое решение.** `esp_firmware/serial_bridge_cpp_reference/` отличался
от рабочего пакета ровно двумя файлами: `frame_parser.hpp` (добавлен
`#include <cmath>` и `|| !std::isfinite(value)`) и `serial_bridge_node.cpp`
(`MSG_ODOMETRY=301`, `MSG_PID=202`, кадр `"$101;%.3f;%.3f;#"`, валидация ID
`0..999` с проверкой целочисленности, **точное** число полей вместо `>=`).
**[Код]**

**Ограничения готового решения.** Копия находилась под `esp_firmware/COLCON_IGNORE`
(colcon её не собирал); `package.xml` и `CMakeLists.txt` объявляли то же имя
пакета `serial_bridge_cpp` — при переносе в корень workspace возник бы конфликт;
её gtest-набор был **идентичен** рабочему и проверял только v1-кадры `$1`/`$2`.
**[Код]**

**Статус после Этапа 2 — закрыто.** Рабочий мост переведён на v2
(`serial_bridge_cpp/include/serial_bridge_cpp/protocol.hpp`, константы и
форматтеры кадров; `serial_bridge_node.cpp:135-191` — `on_cmd_vel` шлёт
`$101;%.3f;%.3f;#`, `on_raw_cmd`/`check_cmd_vel_timeout` шлют `$103;#`).
`frame_parser.hpp` теперь отбрасывает `nan`/`inf`
(`if (num_end != sep || errno == ERANGE || !std::isfinite(value))`).
Reference-копия удалена (`git rm`), её уникальные строки (13 устаревших v1-констант
в `serial_bridge_node.cpp` и 2 строки в README) поглощены рабочей версией.
Проверка: `esp_firmware/tests/test_bridge_v2.cpp` против рабочего include —
exit 0; `test_end_to_end_v2` — exit 0. **[Код]**

### R-02 (высокий). Пользовательские ROS-инструменты несовместимы с v2

**Факт.** `web_regulators_configurator` отправляет `$1`/`$2`/`$3`/`$4`/`$5`
(`web_regulators_configurator/protocol.py:49-74`) и разбирает feedback как
`kind == 1` / `kind == 2` (`node.py:118-137`). `simple_PID_configurator` отправляет

**Следствие.** Настройка ПИ через веб-интерфейс и GUI на прошивке v2 не работает:
все эти ID прошивке неизвестны. **[Код]**

**Дополнительно.** README веб-конфигуратора утверждает «Прошивка ESP32 (≥ 2.1.0)»
и описывает `$1;0;0;#` как STOP — на v2 это неверно. **[Док]**

**Статус после Этапа 2 — закрыто.** `web_regulators_configurator` переведён на v2:
`protocol.py` (`$101`/`$102`/`$103`/`$201`/`$202`/`$204`), `node.py` (`kind == 301`

### R-06 (средний). Конфигурация применяется частично и без подтверждения

**Факт.** `ConfigService` обрезает значения вместо отклонения для SET_FF,
SET_ADRC, SET_REF_FILTER, SET_CTRL_MODE, SET_SPEED_WINDOW
(`config_service.cpp`, функция `constrain`). ACK/NACK реализован только для 210.

**Следствие.** Команда без NACK может быть применена с подменённым значением, о
чём хост не узнает. **[Код]**

**Дополнительный дефект.** При невалидном ПИ для 201/204 выполняется тихий no-op —
без NACK и без изменения счётчиков; для 210 тот же случай корректно возвращает NACK
с ошибкой 1 и корректирует счётчики (`config_service.cpp:124-138`). **[Код]**

**Статус после Этапа 2 — частично закрыто (на стороне хоста).** Веб-конфигуратор
теперь проверяет диапазон ПИД так же, как прошивка (`0..1000`,

прошивке для 201/204 по-прежнему отсутствует — это требует изменения
прошивки, что в Этап 2 не входило. **[Код]**

### R-07 (средний). Отсутствует диапазонная проверка motion-значений

**Факт.** `CommandPolicy::validMotionValues` проверяет только число аргументов и
конечность (`command_policy.h:23-27`). Обрезка по диапазону выполняется позже, в
`MotorController` (`limit = _maxWheelSpeed * 0.8f`; duty в [-1, 1]).

**Следствие.** Команда с `duty = 5.0` принимается, **продлевает watchdog** и затем
молча обрезается до 1.0. Это подтверждённый дефект, а не гипотеза. **[Код]**

**Следствие для безопасности.** Диапазонная проверка отсутствует и в входном
потоке ROS: мост отправляет `%.3f` без ограничений, а `web_regulators_configurator`
ограничивает только свои значения (`max_linear`, `max_angular`, `max_wheel_speed`).

**Решение владельца (2026-11-11).** Поведение прошивки **не меняется**:
диапазонная проверка не добавляется, watchdog продлевается как раньше, обрезка
в `MotorController` остаётся последним рубежом. Дефект сохраняется как
задокументированный остаточный риск (`PROTOCOL.md`, раздел «Motion watchdog»).
Это осознанно принятый риск, а не недосмотр; при изменении отправителей
(`/cmd_vel`, калибровка) диапазон нужно учитывать на стороне хоста.

### R-09 (средний). Отсутствие таймера `/cmd_vel` в мосте

**Факт.** В `serial_bridge_cpp` нет таймера простоя `/cmd_vel`; остановка
источника команд не порождает команду STOP — последняя цель остаётся активной до
срабатывания watchdog прошивки (1 с, `emergency_timer_timeout = 1000`).

**Подтверждение.** Совпадает с записью в корневом `IMPROVEMENTS.md` («Таймаут
`/cmd_vel` в `serial_bridge_cpp`»). **[Код]+[Док]**

**Статус после Этапа 2 — закрыто.** В мост добавлен таймер простоя `/cmd_vel`:
параметр `cmd_vel_timeout` (по умолчанию 0.5 с, `0` выключает проверку),
таймер `create_wall_timer(100 ms)` создаётся только при `cmd_vel_timeout_ > 0.0`,
логика edge-triggered в `check_cmd_vel_timeout()`
(`serial_bridge_node.cpp:167-192`): при простое отправляется `$103;#` — та же
команда остановки, что и у прошивки; сам `$103` watchdog прошивки не продлевает.
Таймер не глушит чужие издатели: raw-кадры движения (`$101`/`$102`/`$104`) из
`serial/cmd` обновляют `last_raw_motion_time_` и снимают таймер
(`on_raw_cmd`, `serial_bridge_node.cpp:153-161`). **[Код]**

### R-11 (закрыто). Длина кадра против размера приёмного буфера ESP32

**Исходная гипотеза.** `SerialReceiver::BUFFER_SIZE = 128` байт
(`serial_receiver.h:12`), тогда как эталонный кодек допускал до
`MAX_FRAME_BYTES = 192` (`esp_firmware/tools/uart_bench/protocol.py`), а буфер
`$405` в `protocol_wrapper.cpp` — 192 Б. Если максимальная длина `$405`
(насыщенные счётчики) превышает 128 Б, такой кадр будет молча потерян на приёме
ESP32.

**Что установлено (подтверждено кодом, расчётом и тестом).**

1. **Направление потока перепутано в гипотезе.** `$405` формирует **прошивка** и
   отправляет Jetson (`protocol_wrapper.cpp:117-129`), поэтому в приёмный буфер
   ESP32 он не попадает вообще. Проверять нужно обратное направление:
   host → ESP32.
2. **Предел приёма прошивки — 127 байт.** `SerialReceiver` пишет символ, пока
   `_index < BUFFER_SIZE - 1` (`serial_receiver.cpp:25`), поэтому максимум —
   127 байт вместе с `$` и `#`. Кадр в 128 байт и более приводит к тихому
   сбросу приёма (`_receiving = false`), **без** пополнения `rejected_commands`.
   **[Код]**
3. **Фактическая длина host → ESP32.** Худшая команда — `$210` (7 полей).
   Консервативная граница (каждое поле — максимальная ширина `format(v, '.9g')`
   для float64, 16 символов) — **125 байт**, запас — **2 байта**. При формате
   `.5f`, который использует `web_regulators_configurator` (|v| ≤ 1000, 11
   символов), — 90 байт. Остальные 19 команд короче; превышений нет. **[Код]**
4. **Обратное направление.** `$405` в худшем случае (12 полей по 10 цифр) —
   140 байт с CRLF; буфер прошивки — 192 Б, приёмник Jetson (`Framer`,
   `MAX_FRAME_BYTES = 192`) и разборщик моста (`FrameParser`, `max_len = 256`)
   его принимают. **[Код]**

**Меры (Этап 6).** Добавлены host-тест границ
(`esp_firmware/tests/test_frame_limits.cpp`, 93 проверки, собирается без `uPID`),
ограничение кодека `uart_bench` на 127 байт для host → ESP32
(`MAX_COMMAND_BYTES`, проверка в `encode()`) и Python-тест
`esp_firmware/tools/uart_bench/test_frame_limits.py`.

**Остаточный риск.** Запас в 2 байта означает, что смена формата вывода числа
(например, переход с `.9g` на `repr()` в Python или добавление поля в `$210`)
вышла бы за предел приёма. Отслеживается двумя способами: тест
`test_frame_limits.cpp` сверяет максимальную длину каждой команды с
`PROTOCOL.md` и с пределом буфера, а `tools/ci/guard.py` проверяет согласованность
ID и комментариев.

**Статус.** Закрыто (Этап 6): дефекта нет, граница зафиксирована контрактом и
автоматическими проверками. **[Код]**

### R-15 (средний). Телеметрия гаснет при простое хоста — требование keep-alive неочевидно

**Факт (подтверждено кодом).** Сторожевой таймер прошивки (1000 мс,
`emergency_timer_timeout` в `config.h`) при простое хоста выполняет аварийную
остановку **и** выключает телеметрию: `safety_manager.cpp` пишет
`ctx_.telemetryEnabled` — это ссылка на глобальный `telemetry_on`
(`esp32_firmware.ino:87, 198`), который читает контур управления
(`control_loop_service.cpp:70`). Включить телеметрию заново можно только
командой `$403;1;#`.

**Следствие.** Хост, который только читает параметры (`$202`, `$206`, `$402`, …),
не продлевает watchdog: watchdog продлевают лишь команды движения 101/102/104
(`command_policy.h::refreshesMotionWatchdog`, `serial_service.cpp:19-27`).
Через 1 с тишины телеметрия пропадает, а повторный `$403;1;#` без команд
движения снова будет отключён ближайшей проверкой watchdog.

**Обнаружено при миграции инструментов.** Скрипты `tools/noisetest.py` и
`tools/steptest.py` ждали телеметрию без команд движения и падали бы на реальной
плате. Исправлено: в цикл включения телеметрии добавлен keep-alive — нулевая
команда движения (`$104;0;0;#` и `$102;0;0;#` соответственно). Это же
требование отражено в `esp_firmware/PROTOCOL.md`.

**Оценка.** Это не дефект прошивки (поведение намеренное и проверяется тестом
шага 4 в `test_glue.cpp`), а ловушка протокола для хостов-читателей. Требует
либо документирования (сделано), либо отдельного решения владельца: считать ли
 watchdog «продлением» и для команд чтения. **[Код]**
