## 1. Итоговая оценка

**Проект готов к рефакторингу локально, но не готов к интеграционному
развёртыванию.**

| Область | Оценка | Обоснование |
|---|---|---|
| Прошивка ESP32 | **готов** к дальнейшему рефакторингу | Слои выделены, политики чистые, сервисы разделены; 14 коммитов в ветке (рефакторинг, тесты, документация); хостовые тесты регулятора проходят |
| ROS-контур (мост) | **готов** к рефакторингу | v2-реализация моста уже написана и проверена host-тестом — её нужно перенести и доработать |
| Интеграция ROS ↔ ESP32 | **не готова** | Рабочий мост на v1, прошивка на v2: ни движение, ни одометрия не работают в связке |
| Инфраструктура сборки/проверок | **не готова** | Нет CI, нет сборки `uPID`, осиротевшие тесты, отсутствие сквозной проверки протокола |
| Безопасность | **ограниченно готова** | Fail-closed политика реализована; аппаратного отключения питания моторов нет; нулевой PWM не подтверждён измерением |
| Документация | **исправлена (Этап 1)** | PROTOCOL.md, README моста, README прошивки и CHANGELOG приведены в соответствие с кодом; `docs/ai/` создана |

**Ключевой вывод.** Проект не требует переписывания: основная работа уже проделана
в ветке, и требуется в основном **доведение миграции протокола до конца** плюс
восстановление автоматической проверяемости. Главный риск — не в сложности кода,
а в том, что объём уже сделанного ничем не защищён от повторного расхождения.

## 2. Подтверждённые проблемы

### R-01 (блокирующий). Разрыв протокола между ROS-мостом и прошивкой

**Факт.** Прошивка реализует только v2 (`command_parser.cpp:decodeCommand` — ID
101…501). Рабочий `serial_bridge_cpp` реализует только v1: шлёт `$1;%.3f;%.3f;#`
(`serial_bridge_node.cpp:128`) и ждёт тип кадра 1 или 2
(`serial_bridge_node.cpp:53-54,229,233`).

**Следствие.** Команда `$1;v;w;#` на прошивке даёт `UNKNOWN` → отбраковка и
инкремент `rejected`; кадр `$301;...;#` мостом не распознаётся → WARN
«Unexpected frame (type 301, 8 fields)». Ни движение, ни одометрия в связке не
работают. **[Код]**

**Доказательство.** `esp_firmware/tests/test_bridge_v2.cpp`, собранный против
рабочего `serial_bridge_cpp/include/serial_bridge_cpp/frame_parser.hpp`, падает с
assertion на `!parse_fields("$301;nan;#", values)` (exit 134, core dumped); та же
проверка против `esp_firmware/serial_bridge_cpp_reference/...` проходит (exit 0).
**[Код]**

**Дополнительно.** Рабочий парсер не проверяет конечность: `frame_parser.hpp:136-139`
использует `strtod` и отбрасывает только `num_end != sep || errno == ERANGE` —
значения `nan`/`inf` проходят и попадают в публикуемую одометрию. **[Код]**

**Где лежит готовое решение.** `esp_firmware/serial_bridge_cpp_reference/` отличается
от рабочего пакета ровно двумя файлами: `frame_parser.hpp` (добавлен
`#include <cmath>` и `|| !std::isfinite(value)`) и `serial_bridge_node.cpp`
(`MSG_ODOMETRY=301`, `MSG_PID=202`, кадр `"$101;%.3f;%.3f;#"`, валидация ID
`0..999` с проверкой целочисленности, **точное** число полей вместо `>=`).
**[Код]**

**Ограничения готового решения.** Копия находится под `esp_firmware/COLCON_IGNORE`
(colcon её не собирает); `package.xml` и `CMakeLists.txt` объявляют то же имя
пакета `serial_bridge_cpp` — при переносе в корень workspace возникнет конфликт;
её gtest-набор **идентичен** рабочему и проверяет только v1-кадры `$1`/`$2`.
**[Код]**

### R-02 (высокий). Пользовательские ROS-инструменты несовместимы с v2

**Факт.** `web_regulators_configurator` отправляет `$1`/`$2`/`$3`/`$4`/`$5`
(`web_regulators_configurator/protocol.py:49-74`) и разбирает feedback как
`kind == 1` / `kind == 2` (`node.py:118-137`). `simple_PID_configurator` отправляет
те же ID (`ros2_node.py:600-665`; `fast_gui_tk.py:569-756`;
`fast_gui_pyside.py:512-593`).

**Следствие.** Настройка ПИ через веб-интерфейс и GUI на прошивке v2 не работает:
все эти ID прошивке неизвестны. **[Код]**

**Дополнительно.** README веб-конфигуратора утверждает «Прошивка ESP32 (≥ 2.1.0)»
и описывает `$1;0;0;#` как STOP — на v2 это неверно. **[Док]**

### R-06 (средний). Конфигурация применяется частично и без подтверждения

**Факт.** `ConfigService` обрезает значения вместо отклонения для SET_FF,
SET_ADRC, SET_REF_FILTER, SET_CTRL_MODE, SET_SPEED_WINDOW
(`config_service.cpp`, функция `constrain`). ACK/NACK реализован только для 210.

**Следствие.** Команда без NACK может быть применена с подменённым значением, о
чём хост не узнает. **[Код]**

**Дополнительный дефект.** При невалидном ПИ для 201/204 выполняется тихий no-op —
без NACK и без изменения счётчиков; для 210 тот же случай корректно возвращает NACK
с ошибкой 1 и корректирует счётчики (`config_service.cpp:124-138`). **[Код]**

### R-07 (средний). Отсутствует диапазонная проверка motion-значений

**Факт.** `CommandPolicy::validMotionValues` проверяет только число аргументов и
конечность (`command_policy.h:23-27`). Обрезка по диапазону выполняется позже, в
`MotorController` (`limit = _maxWheelSpeed * 0.8f`; duty в [-1, 1]).

**Следствие.** Команда с `duty = 5.0` принимается, **продлевает watchdog** и затем
молча обрезается до 1.0. Это подтверждённый дефект, а не гипотеза. **[Код]**

**Следствие для безопасности.** Диапазонная проверка отсутствует и в входном
потоке ROS: мост отправляет `%.3f` без ограничений, а `web_regulators_configurator`
ограничивает только свои значения (`max_linear`, `max_angular`, `max_wheel_speed`).

### R-11 (гипотеза). Длина кадра против размера приёмного буфера ESP32

**Гипотеза.** `SerialReceiver::BUFFER_SIZE = 128` байт (`serial_receiver.h:12`),
тогда как эталонный кодек допускает до `MAX_FRAME_BYTES = 192`
(`tools/uart_bench/protocol.py:5`), а буфер `$405` в `protocol_wrapper.cpp` — 192 Б.
Если максимальная длина `$405` (насыщенные счётчики) превышает 128 Б, такой кадр
будет молча потерян на приёме ESP32.

**Что установлено точно.** При переполнении `SerialReceiver::update()` сбрасывает
приём **молча** — без счётчика и без диагностики
(`serial_receiver.cpp:29-34`); Python-сторона такой случай считает (`Framer.overflow`).

**Что нужно проверить.** Фактическую максимальную длину `$405` при максимальных
значениях счётчиков против 128 Б и убедиться, что `$405` адресуется Jetson, а не
ESP32 (то есть не попадает в приёмный буфер ESP32 вовсе). До проверки это
**не** дефект, а непроверенное предположение.

## 7. Открытые вопросы к владельцу проекта

1. **Шкалы версий.** Три независимые оси (сборка прошивки / версия протокола /
   версия документации) — объединять или разграничить явно? Требуется решение до
   Этапа 4.4.
2. **Аппаратная линия отключения питания моторов.** Планируется ли? Влияет на
   допустимый режим эксплуатации (R-13).
3. **Семантика «мягкой обрезки» конфигурации.** Считать ли это нормой (хост
   должен читать фактическое значение обратно) или дефектом (нужен NACK с
   фактическим применённым значением)? (R-06).
4. **Диапазонная проверка motion-значений.** Отклонять или обрезать? Влияет на
   совместимость с существующими отправителями. (R-07).
5. **Судьба `esp_firmware/serial_bridge_cpp_reference/`.** Удалить после переноса
   или сохранить как эталон в `archive/`? (ADR-008).
6. **Бюджет аппаратной валидации.** Готовы ли предоставить стенд для Этапа 6 —
   без него изменения в прошивке остаются непроверенными на железе.
